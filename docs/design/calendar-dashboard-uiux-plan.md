## 1. 背景と課題認識

### 1.1 現状のUI

- ホーム（SCR-01）: 選択日の体重・食事・筋トレ・ヘルスケアのカードを縦に並べた「1日一覧」。日付移動は前日/翌日ボタンのみ。
- タブ: ホーム / トレーニング / 食事 / 体重 の4タブ。後ろ3つは履歴リスト＋入力導線。
- 推移画面（SCR-02）は要件定義済みだが未実装。グラフは体重履歴内の簡易表示のみ。

### 1.2 課題

1. **記録が前面に出すぎて「見る価値」が薄い。** アプリを開く動機が「入力する時」に限定され、成果を実感する場面（ダッシュボード）がない。継続率＝LTVという戦略（`docs/business/product-strategy.md`）に対して、「続いた記録が誇りになる」体験の受け皿が欠けている。
2. **時間軸の視点がない。** 前日/翌日ボタンでは「今月どれだけやったか」「先週と比べてどうか」が一望できない。筋トレ・体重管理はどちらも継続の可視化が本質なのに、点でしか見えていない。
3. **タブが記録種別で分かれており、ユーザーのメンタルモデル（「今日やったか」「続いているか」「変化したか」）と一致しない。**

### 1.3 再設計の狙い

- **ホーム＝カレンダー。** 開いた瞬間に「今月の自分の頑張り」が面で見える。記録済みの日が視覚的に埋まっていくこと自体が報酬になる（習慣トラッカーの実績あるパターン。GitHubの草、リングの連鎖と同型）。
- **ダッシュボードを独立した1級市民に。** 体重推移と筋トレ実績（ボリューム・頻度・PR）を「確認は0タップに近く」見せる。
- **カレンダーアプリの延長として使える。** iOSホーム画面ウィジェットでカレンダー（記録状況付き）を常時表示し、アプリを開かずに確認・ワンタップで記録開始。

## 2. デザイン原則（本再設計で追加するもの）

既存原則（3タップ記録、入力値保持、黒×ネオンテーマ）を継承した上で追加:

1. **「埋まる快感」を最上位の報酬にする。** カレンダーのセルが記録で光る・埋まることを、数値よりも先に目に入る一次フィードバックとする。
2. **確認は0タップ、記録は3タップ以内。** ホームを開いた時点で今月の状況・今日の状態・ストリークが読み取れる。記録開始はカレンダー上のどの日からでも1タップ。
3. **ダッシュボードは「問い」に答える。** 「体重は減っているか」「トレーニング量は増えているか」「続いているか」の3つの問いに、各カードが1枚で答える。装飾的なグラフは置かない。
4. **過去は編集できる、未来は約束できる（将来拡張）。** カレンダーである以上、将来的には「予定（次の脚の日）」も置けるが、MVPスコープでは過去と今日のみ扱う。

## 3. 情報アーキテクチャの変更

### 3.1 新タブ構成（4タブ → 3タブ）

| タブ | 画面 | 目的 |
|---|---|---|
| ホーム | SCR-01v2 カレンダーホーム | 月間の記録状況を一望し、日を選んで確認・記録する |
| ダッシュボード | SCR-03 ダッシュボード | 体重・筋トレ・食事・ストリークの推移と現在地を確認する |
| 履歴 | SCR-05 履歴ハブ | 種別ごとの全記録リスト（既存のトレーニング/食事/体重リストを統合） |

- 既存の「トレーニング」「食事」「体重」3タブは、SCR-05配下のセグメント切替（またはサブページ）に統合する。既存のリスト実装（`WorkoutListView` / `MealListView` / `BodyWeightListView`）は再利用し、入口だけ変える。
- 設定入口は既存どおり左下歯車（`SettingsAccessButtonModifier`）を維持。
- クイック追加: ホームとダッシュボードの右上に共通「＋」メニュー（体重/食事/トレーニング）を維持。3タップ原則は不変。

### 3.2 画面遷移の骨格

```
[ウィジェット] ─deep link→ ┐
                            ├→ SCR-01v2 カレンダーホーム
                            │     ├─ 日セルタップ → 日サマリーパネル（画面下部、同一画面内）
                            │     │     ├─ カード → 各詳細/編集（既存SCR-11/21/31）
                            │     │     └─ ＋ → 各入力（既存SCR-12/22/32、選択日を引き継ぐ）
                            │     └─ ヘッダーのストリーク → SCR-03へ
                            ├→ SCR-03 ダッシュボード
                            │     └─ 各カード → 対応する履歴/詳細へ
                            └→ SCR-05 履歴ハブ（体重/食事/トレーニング切替）
```

## 4. 画面仕様

### SCR-01v2 カレンダーホーム（SCR-01を置き換え）

#### 構成（上から）

1. **ヘッダー行**
   - 「2026年7月」の月表示＋前月/翌月移動、「今日」ボタン。
   - 右側にストリークバッジ（🔥連続n日）。タップでSCR-03のストリークカードへ。
2. **月間カレンダーグリッド**
   - 7列×5-6行。週の開始曜日は端末設定に従う。
   - **日セルの表現が本設計の核**（§5.1参照）: 記録種別ごとのネオンドットまたはリングで、その日の記録状況を示す。
   - 今日は枠線ハイライト。未来日は減光し選択不可。選択日はアクセント枠。
   - 水平スワイプで前月/翌月。週表示への切替はShould（Q-04）。
3. **選択日サマリーパネル**（カレンダー直下、スクロール領域）
   - 既存ホームの4カード（体重/食事/筋トレ/ヘルスケア）を**コンパクト化**して表示。1カード=1-2行の要約＋未記録なら追加ボタン。
   - カードタップで展開または詳細へ。既存の`HomeView`のカード実装を圧縮して流用する。
   - 初期選択日は今日。

#### 受け入れ条件

- 起動から追加操作なしで、今月の記録状況（どの日に何を記録したか）と今日の要約が1画面で見える。
- 任意の過去日をカレンダーから1タップで選択し、その日の記録確認・追加ができる（既存SCR-01の受け入れ条件をすべて継承）。
- 記録の追加・削除が即座にカレンダーのドット表示へ反映される。
- 月移動が60fpsで滑らかに動作し、月あたりの集計取得で目に見える引っかかりがない。
- VoiceOverで日セルが「7月5日 土曜日、体重・トレーニング記録あり」のように読み上げられる。
- Dynamic Type最大時もカレンダーが破綻しない（セル内はドットのみで文字を持たない設計とする）。

### SCR-03 ダッシュボード（旧SCR-02「推移」を拡張・置換）

#### 構成（上から、カード順は仮置き＝Q-02）

1. **ヒーローカード: ストリーク＆今週サマリー**
   - 連続記録日数、今週のトレーニング回数/先週比、今週の体重変化。
   - 「続いているか」に答える。ホームのストリークバッジと同一データ。
2. **体重カード**
   - 折れ線チャート（Swift Charts）。期間切替 7/30/90日。
   - 7日移動平均線（日々の増減ノイズで一喜一憂させない）、最新値と期間内変化量（-1.2kg等）を大きく表示。
   - 目標体重ラインはShould（Q-05: 目標設定機能が未実装のため）。
3. **筋トレカード（本アプリの主役、面積を最大にする）**
   - 週別総ボリュームの棒グラフ（直近8-12週）。
   - 種目別ベスト（PR）: 主要種目の最高重量×回数を一覧。データは既存`WorkoutSet.volume`と最大重量から算出可能。
   - 実施頻度ヒートマップ（曜日×週のマトリクス、GitHubの草型）はShould。カレンダーホームと表現が重複するため優先度を下げる（Q-06）。
4. **食事カード**
   - 直近7日の摂取カロリー棒グラフ＋PFC平均。
   - 目標カロリー未設定のためターゲット線はShould（Q-05と同根）。
5. **ヘルスケア参考カード**
   - HealthKit連携済みの場合のみ、歩数・睡眠などの参考値。未連携時は小さな導線のみ（既存方針を継承）。

#### 受け入れ条件

- 各カードは「データ2点以上」で意味のあるグラフを描画し、データ不足時は空グラフではなく「記録を始める」導線付きの空状態を表示する。
- チャートのデータ点タップで日付と値を表示し、そこから該当日のカレンダー（SCR-01v2の該当日選択状態）へ遷移できる。
- 期間切替が状態として保持される（タブ離脱→復帰で維持、再起動時は30日にリセットで仮置き）。
- 全チャートがVoiceOverでサマリー（最新値・期間変化）を読み上げ可能。

### SCR-05 履歴ハブ

- 上部セグメントコントロールで トレーニング / 食事 / 体重 を切替。
- 各セグメントの中身は既存の`WorkoutListView` / `MealListView` / `BodyWeightListView`をそのまま埋め込む。
- 既存の詳細・編集・削除フロー（SCR-11〜32）は変更しない。

### WGT-01 ホーム画面ウィジェット（カレンダー型）

- **Sサイズ**: 今日の記録状況（3種のドット）＋ストリーク。タップでアプリのカレンダーホームへ。
- **Mサイズ**: 今週7日分のミニカレンダー行＋記録ドット＋ストリーク。
- **Lサイズ（Should）**: 月間ミニカレンダー＋記録ドット。
- ディープリンク: ウィジェットタップ → 該当日のカレンダーホーム。Mサイズは日セル単位のリンク（iOS 17のウィジェットインタラクション範囲で設計）。
- 黒×ネオンテーマを踏襲し、ロック画面・ホーム画面で「Peak Bodyの見た目」が一目で分かること（シェア映え戦略との一貫性）。
- 記録入力そのものはウィジェットからは行わない（MVP）。確認0タップ＋起動短縮に絞る。

## 5. コンポーネント仕様

### 5.1 日セル記録インジケーター（最重要コンポーネント）

- 1つの日セルに最大3種の記録状態を表現する: 体重（ライム）/ 食事（ネオン紫）/ トレーニング（ネオンブルー）。色は`PeakTheme`の既存アクセントに揃え、design エージェントが最終決定する。
- 第1案: セル下部に最大3つの小ドット。第2案: 3分割リング（アクティビティリング風）。**designエージェントは両案をモック比較し、視認性（小セル・Dynamic Type・色覚多様性）で決定する。** 色だけに依存せず、ドット位置（左=体重、中=食事、右=筋トレ）を固定して冗長化する。
- トレーニング記録日はドットを一段強く光らせる（本アプリの主役の強調＋「草が濃い」表現の簡易版）。
- SwiftUIの単一Viewとして実装し、カレンダーセル・ウィジェット・履歴の行頭で共用する。

### 5.2 月間記録サマリーの供給API（RecordStore拡張)

カレンダー描画に必要な集計をStoreに追加する:

```
struct DayRecordFlags { let hasBodyWeight, hasMeal, hasWorkout: Bool; let workoutVolume: Double }
func monthlyFlags(for month: Date) -> [Date: DayRecordFlags]
func currentStreak(asOf: Date) -> Int   // 「いずれかの記録がある日」の連続数（定義はQ-03）
```

- 月移動のたびに全記録を線形走査しない構造（日付キーの索引 or キャッシュ）をarchitectエージェントが設計する。ウィジェットからも同じ集計を使うため、共有可能なモジュールに置く。

### 5.3 チャートコンポーネント

- Swift Chartsで実装。カードごとに個別実装せず、`PeakChartCard`（タイトル/期間切替/空状態/データ点選択を内蔵）を共通化する。
- 空状態・1点のみ・大量データ（90日）の3状態を必ずプレビューに持つ。

## 6. 技術的前提と影響範囲（architect / swiftエージェント向け）

1. **ウィジェット化にはデータ層の共有が必須。** 現在の`RecordStore`はアプリサンドボックス内のローカルJSON保存。ウィジェット（別プロセス）から読むには **App Group コンテナへの保存場所移行**が必要。あわせてSwiftData移行の判断（HANDOFF既出の課題）をこのタイミングで行うのが合理的。→ Phase 3の前提タスク。
2. **カレンダーの日付計算**は`Calendar.autoupdatingCurrent`基準、週開始曜日・タイムゾーン変更・うるう月をqa観点に含める。
3. **パフォーマンス**: 月間集計はO(記録数)の全走査で開始してよいが、`monthlyFlags`をインターフェースとして固定し、内部を後から索引化できるようにする。
4. **既存画面の再利用**: 入力フォーム（SCR-12/22/32）、詳細（SCR-11/21/31）、リスト3種は無変更で流用。変更が及ぶのは`ContentView`（タブ）、`HomeView`（置換）、`RecordStore`（集計API追加）に限定する。
5. **ローカライズ**: 新規文言はすべて`AppLocalization`のキー追加で行う（直書き禁止、既存ルール踏襲）。

## 8. 成功指標（UX KPI）

`docs/business/product-strategy.md`のKPIを継承し、本再設計で特に動かすもの:

| 指標 | 現状仮説 | 目標 |
|---|---|---|
| 記録を伴わないアプリ起動（＝見るためだけの起動）の割合 | ほぼ0 | 30%以上 |
| 7日間で3日以上記録した利用者の割合 | — | 40%以上 |
| ウィジェット設置率（Phase 3後） | — | 30%以上 |
| 起動→今日の記録開始のタップ数 | 1-2 | 悪化させない（≦2） |

計測手段はMVP時点で未整備のため、Phase 4でのアナリティクス導入までは定性確認とする（PMエージェントは指標をタスク化しないこと）。

## 9. リスクと対応

| リスク | 対応 |
|---|---|
| カレンダー化で「今日の入力」への導線が1タップ増える | ホーム初期状態を「今日選択済み＋サマリーパネル表示」とし、追加ボタンを即座に押せる位置に固定する |
| 記録が少ない初週はカレンダーが「空白の面」になり逆効果 | 空セルは無彩色で沈め、記録済みセルの発光を強調。初回はオンボーディング的に「今日を記録して最初の1マスを光らせよう」の空状態文言を出す |
| App Group移行でのデータマイグレーション失敗 | 移行時に旧パスからのワンタイムコピー＋検証を実装し、qaが新規/更新両インストール経路を確認する |
| ドット3色が小セルで判別不能 | 位置固定＋形状差の冗長化（§5.1）。designがモック段階で実寸検証する |
